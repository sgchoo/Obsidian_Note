# TCP/UDP 차이점과 QUIC 정리
---

## 1. OSI 7계층에서 TCP/UDP의 위치

OSI 7계층 모델에서 TCP와 UDP는 모두 **4계층(Transport Layer, 전송 계층)** 에 위치한 프로토콜입니다. 같은 계층에 있다는 것은 곧, "위 계층(Application)에서 내려온 데이터를 어떻게 목적지까지 실어 나를 것인가"에 대해 서로 다른 답을 내놓는 두 가지 방식이라는 뜻입니다.

```
7. Application  (HTTP, FTP, DNS, SMTP ...)        ← 애플리케이션이 사용하는 프로토콜
8. Presentation (인코딩, 암호화, 압축)
9. Session      (세션 수립/유지/종료)
─────────────────────────────────────────
10. Transport    (TCP, UDP)                        ← 여기!
─────────────────────────────────────────
11. Network      (IP, ICMP, 라우팅)
12. Data Link    (Ethernet, MAC, 스위칭)
13. Physical     (전기 신호, 광신호, 케이블)
```

### 왜 하필 4계층인가

- 3계층(Network/IP)까지는 "패킷을 어떻게 목적지 IP까지 라우팅할 것인가"만 책임집니다. IP는 **best-effort** 방식이라 패킷이 유실되든, 순서가 바뀌든 신경 쓰지 않습니다.
- 4계층은 이 위에서 **Port 번호로 프로세스(애플리케이션)를 구분**하고, 필요하다면 신뢰성·순서·흐름 제어까지 책임지는 계층입니다.
- 즉 TCP/UDP의 차이는 "3계층이 보장하지 않는 것들을 4계층에서 얼마나 보완할 것인가"에 대한 설계 철학의 차이입니다.

|계층|책임|TCP/UDP와의 관계|
|---|---|---|
|L3 (Network)|IP 주소 기반 라우팅, best-effort 전달|유실/순서 문제를 그대로 방치|
|L4 (Transport)|Port 기반 프로세스 구분, (선택적) 신뢰성 보장|TCP는 보완, UDP는 방치|
|L5~L7 (Session~Application)|애플리케이션 로직, 세션 관리|TCP/UDP가 보장 안 하는 부분을 직접 구현하기도 함 (QUIC이 대표적)|

## 2. TCP (Transmission Control Protocol)

**연결 지향형(Connection-oriented)** 프로토콜로, L3(IP)가 방치한 신뢰성·순서 문제를 L4에서 직접 해결합니다.

### 핵심 메커니즘

1. **3-way Handshake (연결 수립)** `SYN` → `SYN-ACK` → `ACK` 순으로 논리적 연결을 먼저 맺습니다.
2. **신뢰성 보장** 각 세그먼트에 시퀀스 번호를 부여하고 ACK로 수신을 확인합니다. 일정 시간 내 ACK가 없으면 재전송합니다.
3. **순서 보장** 시퀀스 번호 기반으로 수신 측에서 도착한 세그먼트를 재조립합니다.
4. **흐름 제어 (Flow Control)** 슬라이딩 윈도우로 수신자의 처리 속도에 맞춰 송신 속도를 조절합니다.
5. **혼잡 제어 (Congestion Control)** Slow Start, Congestion Avoidance 등으로 네트워크 혼잡도를 감지하고 전송률을 동적으로 조정합니다.
6. **연결 종료** 4-way handshake (`FIN` → `ACK` → `FIN` → `ACK`)로 연결을 정리합니다.

### 비용

- 헤더 크기 최소 20바이트
- 연결 수립/종료에 드는 RTT(Round Trip Time) 비용
- 재전송/혼잡제어로 인한 지연 가능성

## 3. UDP (User Datagram Protocol)

**비연결형(Connectionless)** 프로토콜로, L3(IP)의 best-effort 특성을 그대로 L4까지 끌고 올라옵니다.

### 핵심 특징

- **핸드셰이크 없음**: 상대의 상태를 확인하지 않고 바로 데이터그램을 전송합니다.
- **신뢰성 없음**: ACK, 재전송, 순서 보장 메커니즘이 전혀 없습니다. 유실되면 그대로 유실됩니다.
- **가벼운 헤더**: 8바이트 (출발지 Port, 목적지 Port, 길이, 체크섬)만 존재합니다.
- **혼잡 제어 없음**: 네트워크 상황과 무관하게 애플리케이션이 원하는 만큼 전송합니다. (단, 필요 시 애플리케이션이 직접 구현)

### 왜 여전히 쓰이는가

신뢰성 보장 로직 자체가 지연(latency)의 원인이 되기 때문에, "패킷 한두 개 유실보다 실시간성이 더 중요한" 도메인에서는 UDP가 유리합니다. (DNS 질의, 스트리밍, 온라인 게임, VoIP 등)

---

## 4. TCP vs UDP 비교 요약

|항목|TCP|UDP|
|---|---|---|
|OSI 계층|L4 (Transport)|L4 (Transport)|
|연결 방식|연결 지향 (3-way handshake)|비연결형|
|신뢰성|보장 (ACK, 재전송)|보장 안 함|
|순서 보장|O|X|
|흐름/혼잡 제어|O|X (기본)|
|헤더 크기|최소 20바이트|8바이트|
|속도/지연|상대적으로 느림|빠름|
|대표 사용처|HTTP/1.1, HTTP/2, FTP, SMTP|DNS, 스트리밍, 온라인 게임, VoIP|

**핵심 요약**: TCP는 "정확성"을, UDP는 "속도와 실시간성"을 우선시하는 설계 철학의 차이입니다.

## 5. QUIC (Quick UDP Internet Connections)

QUIC은 Google이 설계하고 이후 IETF에서 표준화(RFC 9000, 2021년)한 프로토콜입니다. **UDP(L4) 위에서 동작하면서, TCP의 신뢰성·순서 보장과 TLS의 보안성을 애플리케이션(유저스페이스) 레벨에서 재구현**한 것이 핵심입니다. HTTP/3의 전송 계층으로 채택되었습니다.

### OSI 계층 관점에서 QUIC의 위치

QUIC은 전통적인 OSI 계층 구분으로는 딱 떨어지지 않는 프로토콜입니다. L4(UDP)를 그대로 사용하면서, 원래 L4(TCP의 신뢰성)와 L5~L6(세션, 암호화/TLS)이 담당하던 역할까지 끌어와 하나로 통합했기 때문입니다.

```
[HTTP/2 + TLS 1.2 스택]              [HTTP/3 (QUIC) 스택]
L7 Application : HTTP/2              L7 Application : HTTP/3
L6 Presentation: TLS (별도 계층)      L5~L6         : QUIC이 통합 처리
L4 Transport   : TCP                 L4 Transport   : UDP (QUIC이 그 위에서 동작)
L3 Network     : IP                  L3 Network     : IP
```

즉 QUIC은 "커널이 담당하던 TCP 로직 + TLS 로직"을 유저스페이스로 끌어올려 하나의 계층처럼 묶어버린 설계입니다.

### 왜 UDP 위에 만들었는가

- TCP는 커널(OS) 레벨에 구현되어 있어, 알고리즘을 개선하려면 OS 커널 업데이트가 필요하고 전 세계 배포 속도가 매우 느립니다.
- UDP는 커널이 아무 처리도 하지 않는 "빈 도로"와 같으므로, 그 위에 필요한 로직을 **애플리케이션 레벨**에서 구현하면 브라우저/서버 업데이트만으로 빠르게 개선하고 배포할 수 있습니다.

### 핵심 특징

1. **연결 수립 지연 감소 (0-RTT / 1-RTT)**
    
    - 기존 TCP + TLS 1.2는 연결에 최소 2~3 RTT가 필요했습니다 (TCP handshake + TLS handshake가 별도로 진행).
    - QUIC은 전송 계층에 **TLS 1.3을 통합**하여, 최초 연결도 1-RTT, 이미 통신한 적 있는 서버로의 재연결은 0-RTT로 처리합니다.
2. **Head-of-Line Blocking(HOL Blocking) 해결**
    
    - TCP 기반 HTTP/2는 하나의 TCP 연결에서 여러 스트림을 다중화하는데, TCP 자체가 순서 보장을 하다 보니 패킷 하나가 유실되면 그 뒤의 모든 스트림이 대기해야 했습니다.
    - QUIC은 스트림별로 독립적인 시퀀싱과 재전송을 수행하여, 한 스트림의 패킷 유실이 다른 스트림에 영향을 주지 않습니다.
3. **Connection Migration**
    
    - TCP 연결은 4-tuple(출발지 IP/Port, 목적지 IP/Port)로 식별되어, IP가 바뀌면(Wi-Fi ↔ LTE 전환 등) 연결이 끊깁니다.
    - QUIC은 **Connection ID**로 연결을 식별하므로 IP가 바뀌어도 연결이 유지됩니다. 모바일 환경에서 특히 유리합니다.
4. **암호화가 기본값**
    
    - QUIC 패킷은 일부 헤더를 제외하고 대부분 암호화됩니다. TLS 1.3이 필수로 통합되어 있어, 평문(암호화되지 않은) QUIC은 존재하지 않습니다.
5. **자체 혼잡 제어**
    
    - 커널 레벨 TCP 스택에 의존하지 않고, 애플리케이션(브라우저/서버)이 자체적으로 혼잡 제어 알고리즘(CUBIC, BBR 등)을 구현하고 교체할 수 있습니다.

### 정리

QUIC은 "UDP의 속도"와 "TCP의 신뢰성/순서 보장", 그리고 "TLS의 보안"을 하나로 묶어 **전송 계층 로직을 유저 스페이스로 끌어올린** 설계입니다. HOL Blocking 해소와 빠른 핸드셰이크가 실질적 이득이며, 지연이 중요한 웹 서비스(HTTP/3)나 모바일 환경에서 채택이 계속 늘고 있습니다.

## 6. 실무 관점 참고

- 일반적인 REST API 서버(Nest.js, Spring Boot 등)는 TCP 기반(HTTP/1.1, HTTP/2)으로 충분한 경우가 대부분입니다.
- 실시간성이 중요한 서비스(게임 서버, 화상 통화, 라이브 스트리밍, gRPC 스트리밍)를 설계할 때는 UDP 기반 프로토콜이나 QUIC 도입을 검토합니다.
- 최근 브라우저(Chrome, Firefox 등)와 CDN(Cloudflare, Google 등)은 HTTP/3(QUIC)을 기본 지원하므로, 클라이언트-서버 통신 최적화 시 고려 대상이 됩니다.
