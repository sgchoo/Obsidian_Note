# 서버 개발의 기본 보안: 인증과 인가

서버 개발에서 가장 기본적인 보안 개념은 **인증(Authentication)** 과 **인가(Authorization)** 이다.

## 1. 인증과 인가

### 인증(Authentication)

인증은 **사용자가 누구인지 확인하는 과정**이다.

예를 들어 사용자가 아이디와 비밀번호를 입력하면, 서버는 해당 정보가 올바른지 확인한다.

```text
사용자 로그인 요청
→ 아이디 / 비밀번호 검증
→ 사용자가 누구인지 확인
````

인증에 성공하면 서버는 클라이언트에게 토큰이나 세션 정보를 제공한다.

---

### 인가(Authorization)

인가는 **인증된 사용자가 특정 자원에 접근할 권한이 있는지 확인하는 과정**이다.

예를 들어 로그인한 사용자라고 해도, 다른 사용자의 개인정보나 관리자 페이지에 접근할 수 있으면 안 된다.

```text
사용자 요청
→ 인증 여부 확인
→ 해당 자원에 접근할 권한이 있는지 확인
→ 허용 또는 거부
```

즉, 인증은 **“누구인가?”** 를 확인하는 것이고,  
인가는 **“무엇을 할 수 있는가?”** 를 확인하는 것이다.

---

## 2. 인증 성공 후 토큰 발급

사용자가 누구인지 확인하는 데 성공하면, 서버는 클라이언트에게 문자열 형태의 **토큰**을 제공할 수 있다.

클라이언트는 이후 요청을 보낼 때 이 토큰을 함께 전송한다.

```text
로그인 성공
→ 서버가 토큰 발급
→ 클라이언트가 토큰 저장
→ 이후 요청마다 토큰 전송
→ 서버가 토큰 검증
```

---

## 3. 서버 저장소 기반 토큰 방식

서버는 토큰과 사용자 식별 정보를 DB, Redis 같은 외부 저장소에 보관할 수 있다.

로그인에 성공하면 서버는 임의의 토큰 문자열을 만든 뒤, 해당 토큰과 사용자 정보를 저장소에 매핑한다.

```text
token_abc123 → userId: 1
```

외부 저장소에 보관되는 정보는 보통 다음과 같다.

- 토큰
- 사용자 식별자
- 생성 시간
- 최근 사용 시간
- 만료 시간
- 클라이언트 정보
- IP 정보
- 디바이스 정보
- 클라이언트 버전 등


이 방식은 서버가 저장소에서 토큰 정보를 직접 조회하기 때문에, 토큰을 강제로 만료시키거나 로그아웃 처리하기 쉽다.

예를 들어 사용자가 로그아웃하면 Redis나 DB에서 해당 토큰을 삭제하면 된다.

---

## 4. 서버 메모리 기반 세션 방식

외부 저장소가 아닌 **서버 메모리**에 인증 정보를 저장할 수도 있다.

대표적인 예가 **서블릿 세션**이다.

서블릿 기반 서버에서는 로그인에 성공하면 서버가 세션을 만들고, 클라이언트에게 세션 ID를 전달한다.

```text
클라이언트 쿠키: JSESSIONID=abc123
서버 메모리: abc123 → userId: 1
```

이후 클라이언트는 요청마다 `JSESSIONID` 쿠키를 함께 보내고, 서버는 해당 세션 ID를 이용해 사용자를 확인한다.

다만 서버 메모리에 세션을 저장하면 서버가 여러 대일 때 문제가 생길 수 있다.

예를 들어 A 서버에 로그인 세션이 저장되어 있는데, 다음 요청이 B 서버로 가면 B 서버는 해당 세션을 알 수 없다.

이를 해결하기 위해 다음과 같은 방법을 사용한다.

- Sticky Session 사용
- Redis 같은 외부 세션 저장소 사용
- JWT 같은 Stateless 인증 방식 사용


---

## 5. JWT 방식

토큰 자체에 사용자 식별 정보를 담을 수도 있다.

대표적인 방식이 **JWT(JSON Web Token)** 이다.

JWT는 보통 다음과 같은 정보를 담는다.

- 사용자 식별자
    
- 권한 정보
    
- 발급 시간
    
- 만료 시간
    

JWT는 서버가 토큰 내부의 정보를 읽고 서명을 검증해서 사용자를 확인할 수 있다.

```text
클라이언트 요청
→ JWT 전달
→ 서버가 JWT 서명 검증
→ 사용자 정보 확인
```

JWT의 장점은 서버가 세션 정보를 별도로 저장하지 않아도 된다는 점이다.

이런 방식을 **Stateless 인증**이라고 한다.

다만 JWT는 한 번 발급되면 만료 시간 전까지 계속 유효할 수 있기 때문에, 강제 로그아웃이나 토큰 폐기 처리가 상대적으로 어렵다.

이를 보완하기 위해 다음과 같은 방식을 함께 사용한다.

- Access Token 만료 시간을 짧게 설정
    
- Refresh Token 사용
    
- Refresh Token은 DB나 Redis에 저장
    
- 탈취된 토큰을 차단하기 위한 블랙리스트 사용
    

---

## 6. Access Token과 Refresh Token

실무에서는 보통 Access Token과 Refresh Token을 함께 사용한다.

### Access Token

Access Token은 API 요청에 사용되는 토큰이다.

보통 만료 시간을 짧게 설정한다.

```text
Authorization: Bearer access_token
```

Access Token이 탈취되더라도 짧은 시간 후 만료되기 때문에 피해를 줄일 수 있다.

---

### Refresh Token

Refresh Token은 Access Token을 다시 발급받기 위한 토큰이다.

보통 Access Token보다 만료 시간이 길다.

```text
Access Token 만료
→ Refresh Token으로 재발급 요청
→ 새 Access Token 발급
```

Refresh Token은 탈취되면 위험하기 때문에 DB나 Redis에 저장하고, 필요하면 강제로 만료시킬 수 있도록 관리하는 경우가 많다.

---

## 7. 토큰 전송 방식

토큰은 보통 다음 두 가지 방식으로 전송한다.

## 7.1 쿠키 방식

토큰을 쿠키에 저장해서 서버로 전송하는 방식이다.

```text
Cookie: accessToken=abc123
```

쿠키 방식은 브라우저가 요청마다 자동으로 쿠키를 전송한다는 장점이 있다.

하지만 쿠키를 사용하면 CSRF 공격을 고려해야 한다.

보안을 위해 다음 설정을 함께 사용하는 것이 좋다.

- HttpOnly
    
- Secure
    
- SameSite
    
- 만료 시간 설정
    

### HttpOnly

JavaScript에서 쿠키에 접근하지 못하게 하는 설정이다.

XSS 공격으로 토큰이 탈취되는 위험을 줄일 수 있다.

### Secure

HTTPS 환경에서만 쿠키가 전송되도록 하는 설정이다.

### SameSite

다른 사이트에서 요청할 때 쿠키가 함께 전송되는 것을 제한한다.

CSRF 공격을 줄이는 데 도움이 된다.

---

## 7.2 Authorization 헤더 방식

토큰을 HTTP Authorization 헤더에 담아서 전송하는 방식이다.

```text
Authorization: Bearer access_token
```

이 방식은 모바일 앱, SPA, 외부 API 서버 간 통신에서 자주 사용된다.

헤더 방식은 브라우저가 자동으로 토큰을 붙이지 않기 때문에 CSRF 위험은 상대적으로 낮다.

다만 토큰을 localStorage에 저장하면 XSS 공격에 취약할 수 있다.

---

## 8. 비밀번호 저장

인증에서 중요한 또 다른 부분은 비밀번호 저장 방식이다.

서버는 사용자의 비밀번호를 절대 평문으로 저장하면 안 된다.

비밀번호는 반드시 해시 함수를 이용해 변환한 뒤 저장해야 한다.

대표적으로 다음과 같은 알고리즘을 사용한다.

- bcrypt
    
- scrypt
    
- Argon2
    

```text
사용자 비밀번호: password123
→ 해시 처리
→ DB에는 해시된 값만 저장
```

로그인 시에는 사용자가 입력한 비밀번호를 다시 해시 처리한 뒤, DB에 저장된 해시 값과 비교한다.

---

## 9. 인가 처리 방식

인가를 처리할 때는 사용자가 어떤 권한을 가지고 있는지 확인해야 한다.

대표적인 방식은 다음과 같다.

## 9.1 Role 기반 인가

사용자에게 역할을 부여하는 방식이다.

```text
USER
ADMIN
MANAGER
```

예를 들어 관리자 페이지는 `ADMIN` 권한을 가진 사용자만 접근할 수 있도록 제한한다.

```text
관리자 API 요청
→ 사용자 권한 확인
→ ADMIN이면 허용
→ 아니면 거부
```

이를 **RBAC(Role-Based Access Control)** 라고 한다.

---

## 9.2 소유자 기반 인가

실무에서는 단순히 역할만 확인해서는 부족한 경우가 많다.

예를 들어 일반 사용자는 자신의 게시글은 수정할 수 있지만, 다른 사람의 게시글은 수정할 수 없어야 한다.

```text
게시글 수정 요청
→ 로그인 사용자 ID 확인
→ 게시글 작성자 ID 확인
→ 둘이 같으면 허용
→ 다르면 거부
```

이런 처리가 제대로 되어 있지 않으면 IDOR 취약점이 발생할 수 있다.

IDOR는 사용자가 URL이나 요청 값의 ID를 바꿔서 다른 사용자의 자원에 접근하는 취약점이다.

```text
/users/1/orders
/users/2/orders
```

서버는 단순히 로그인 여부만 확인하면 안 되고, 해당 사용자가 그 자원에 접근할 권한이 있는지도 반드시 확인해야 한다.

---

## 10. HTTPS 사용

토큰, 쿠키, 비밀번호 같은 민감한 정보는 네트워크를 통해 전송된다.

따라서 반드시 HTTPS를 사용해야 한다.

HTTPS를 사용하지 않으면 중간에서 요청 내용을 가로채는 공격에 취약해질 수 있다.

```text
HTTP  → 평문 전송
HTTPS → 암호화 전송
```

---

## 11. 인증과 인가에서 주의할 점

인증과 인가를 구현할 때는 다음 사항을 주의해야 한다.

- 비밀번호를 평문으로 저장하지 않는다.
    
- 토큰 만료 시간을 설정한다.
    
- Access Token은 짧게 유지한다.
    
- Refresh Token은 안전하게 저장한다.
    
- 로그아웃 시 Refresh Token을 폐기한다.
    
- HTTPS를 사용한다.
    
- 쿠키 사용 시 HttpOnly, Secure, SameSite 설정을 적용한다.
    
- 관리자 API는 반드시 권한을 확인한다.
    
- 사용자 자원 접근 시 소유자 검사를 한다.
    
- 클라이언트에서 숨긴 버튼만 믿지 않는다.
    
- 최종 권한 검사는 반드시 서버에서 한다.
    

---

## 12. 정리

인증은 사용자가 누구인지 확인하는 과정이고, 인가는 해당 사용자가 특정 자원에 접근할 수 있는지 확인하는 과정이다.

인증 방식은 크게 서버 저장소 기반 방식과 JWT 기반 방식으로 나눌 수 있다.

서버 저장소 기반 방식은 토큰을 쉽게 폐기할 수 있지만, 저장소 조회가 필요하다.

JWT 방식은 서버가 별도의 세션 저장소 없이 토큰을 검증할 수 있지만, 한 번 발급된 토큰을 즉시 폐기하기 어렵다.

토큰은 쿠키나 Authorization 헤더를 통해 전송할 수 있으며, 각각의 방식에 따라 XSS, CSRF 같은 보안 위험을 고려해야 한다.

결국 서버 보안에서 중요한 것은 단순히 로그인 기능을 구현하는 것이 아니라, 사용자가 요청한 자원에 접근할 권한이 있는지 서버에서 끝까지 검증하는 것이다.
