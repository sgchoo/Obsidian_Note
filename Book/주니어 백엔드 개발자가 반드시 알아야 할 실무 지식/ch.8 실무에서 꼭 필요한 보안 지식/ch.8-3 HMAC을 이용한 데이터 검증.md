# HMAC과 API Key 인증

## 1. HMAC이란?

**HMAC**은 `Hash-based Message Authentication Code`의 약자이다.

HMAC은 **해시 함수와 비밀 키를 이용해서 메시지의 신뢰성을 검증하는 방식**이다.

쉽게 말하면, 클라이언트와 서버가 같은 비밀 키를 알고 있고, 클라이언트는 요청 내용을 비밀 키로 서명해서 서버에 보낸다.

서버는 같은 비밀 키로 다시 서명을 계산한 뒤, 클라이언트가 보낸 서명과 비교한다.

```text
클라이언트:
요청 데이터 + 비밀 키
→ HMAC 서명 생성
→ 서버에 요청 데이터와 서명 전송

서버:
받은 요청 데이터 + 서버가 가진 비밀 키
→ HMAC 서명 재계산
→ 클라이언트가 보낸 서명과 비교
````

두 서명이 같으면 서버는 해당 요청을 신뢰할 수 있다.

---

## 2. HMAC이 보장하는 것

HMAC은 해시 함수와 비밀 키를 이용해서 다음 두 가지를 보장한다.

### 2.1 메시지 무결성

메시지 무결성이란 **메시지가 중간에 위변조되지 않았음을 확인할 수 있는 성질**이다.

예를 들어 클라이언트가 다음 요청을 보냈다고 하자.

```json
{
  "amount": 10000
}
```

그런데 중간에서 공격자가 값을 바꾼다.

```json
{
  "amount": 1000000
}
```

요청 내용이 바뀌면 서버가 다시 계산한 HMAC 서명도 달라진다.

따라서 서버는 클라이언트가 보낸 서명과 서버가 계산한 서명이 다르다는 것을 보고, 요청이 변조되었다고 판단할 수 있다.

```text
요청 내용이 바뀜
→ HMAC 값도 달라짐
→ 서명 검증 실패
→ 요청 거부
```

---

### 2.2 인증

HMAC은 **메시지 발신자를 인증하는 데도 사용할 수 있다.**

올바른 HMAC 서명을 만들려면 비밀 키를 알고 있어야 한다.

따라서 서버는 서명이 올바르면 다음과 같이 판단할 수 있다.

```text
이 요청은 비밀 키를 알고 있는 클라이언트가 만든 요청이다.
```

즉, HMAC은 단순히 메시지가 변조되지 않았는지만 확인하는 것이 아니라, **해당 요청이 신뢰할 수 있는 발신자로부터 왔는지도 확인**할 수 있다.

---

## 3. API Key와 HMAC의 차이

API Key와 HMAC은 비슷해 보이지만 역할이 다르다.

```text
API Key
→ 클라이언트를 식별하는 값

HMAC
→ 요청이 변조되지 않았고, 비밀 키를 가진 클라이언트가 보낸 요청인지 검증하는 방식
```

API Key만 사용하는 경우는 다음과 같다.

```http
GET /api/orders
x-api-key: client_123
```

서버는 `client_123`이라는 API Key가 유효한지만 확인한다.

```text
API Key가 유효함
→ 요청 허용
```

하지만 API Key가 탈취되면 공격자가 그대로 사용할 수 있다는 문제가 있다.

---

## 4. API Key + HMAC 방식

HMAC을 사용하는 API 인증에서는 보통 API Key와 Secret Key를 함께 사용한다.

```text
API Key
→ 클라이언트 식별용

Secret Key
→ HMAC 서명 생성용 비밀 키
```

요청 예시는 다음과 같다.

```http
POST /api/orders
x-api-key: client_123
x-timestamp: 1710000000
x-signature: 9f2a8c...
```

서명은 보통 다음 정보들을 조합해서 만든다.

```text
HTTP Method
+ 요청 URL
+ 요청 Body
+ Timestamp
+ Secret Key
```

예를 들면 다음과 같다.

```text
POST
/api/orders
{"productId":1,"count":2}
1710000000
secret_key
```

이 값을 HMAC-SHA256 같은 알고리즘으로 계산해서 `x-signature`에 담아 보낸다.

---

## 5. 서버의 검증 과정

서버는 먼저 API Key로 클라이언트를 찾는다.

```text
x-api-key: client_123
```

그다음 DB나 Redis 등에 저장된 Secret Key를 조회한다.

```text
client_123 → secret_key
```

그리고 클라이언트가 보낸 요청 내용으로 HMAC 서명을 다시 계산한다.

```text
요청 Method + URL + Body + Timestamp + Secret Key
→ 서버 측 HMAC 서명 생성
```

마지막으로 클라이언트가 보낸 `x-signature`와 서버가 계산한 서명을 비교한다.

```text
두 서명이 같음
→ 정상 요청

두 서명이 다름
→ 변조되었거나 잘못된 요청
```

---

## 6. 재전송 공격 방지

HMAC만 사용하면 이전에 보냈던 정상 요청을 누군가 다시 보내는 공격을 막기 어렵다.

이를 **재전송 공격**이라고 한다.

```text
정상 요청을 가로챔
→ 같은 요청을 나중에 다시 전송
```

이를 막기 위해 보통 `timestamp`를 함께 사용한다.

```http
x-timestamp: 1710000000
```

서버는 timestamp가 현재 시간과 너무 차이 나는 경우 요청을 거부한다.

```text
현재 시간 기준 5분 이상 차이남
→ 오래된 요청으로 판단
→ 거부
```

더 강하게 막고 싶다면 `nonce`라는 일회용 값을 함께 사용할 수도 있다.

```http
x-nonce: random-unique-value
```

서버는 이미 사용된 nonce를 저장해두고, 같은 nonce가 다시 들어오면 요청을 거부한다.

---

## 7. 정리

HMAC은 API Key 그 자체가 아니다.

API Key는 클라이언트를 식별하기 위한 값이고, HMAC은 요청의 신뢰성을 검증하기 위한 서명 방식이다.

HMAC은 다음 두 가지를 보장한다.

```text
1. 메시지 무결성
   → 메시지가 중간에 위변조되지 않았음을 확인할 수 있다.

2. 인증
   → 비밀 키를 가진 발신자가 만든 메시지임을 확인할 수 있다.
```

따라서 API Key 인증을 더 안전하게 만들고 싶다면 다음과 같은 구조를 사용할 수 있다.

```text
API Key로 클라이언트를 식별하고
→ Secret Key를 조회하고
→ 요청 내용을 HMAC으로 검증한다
```

즉, 실무에서 HMAC은 **API Key 인증에 서명 검증을 추가해서 보안을 강화하는 방식**이라고 이해하면 된다.
