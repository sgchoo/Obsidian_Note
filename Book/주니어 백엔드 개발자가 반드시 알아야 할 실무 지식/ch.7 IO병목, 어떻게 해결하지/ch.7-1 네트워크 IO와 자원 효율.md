# 네트워크 I/O와 자원 효율 정리

## 핵심 요약

**문제의 본질**: 서버는 본질적으로 네트워크 프로그램이며(DB, Redis, 외부 API 호출 등), I/O 작업 중 스레드는 블로킹되어 CPU를 활용하지 못한다. 이를 해결하려 스레드를 무한정 늘리면 메모리와 컨텍스트 스위칭이 새로운 병목이 된다.

**해결 방향**: ① 경량 스레드(가상 스레드, 고루틴, 코루틴) ② 논블로킹/비동기 I/O

---

### 1. 스레드가 블로킹된다
`read()` 호출 시 데이터가 도착하지 않았다면, OS 커널은 해당 스레드를 **`TASK_INTERRUPTIBLE` 상태**로 전환하고 실행 큐(run queue)에서 제거한다. 즉, 스레드는 단순히 "기다리는" 게 아니라 **스케줄링 대상에서 빠진다**. 데이터가 도착하면 커널이 다시 깨워서 실행 큐에 넣는다.

이게 중요한 이유는, "대기"라는 표현은 마치 CPU를 점유한 채 폴링하는 것처럼 오해될 수 있기 때문이다. 실제로 블로킹 I/O 중에는 CPU를 점유하지 않는다. 문제는 **CPU가 아니라 스레드라는 자원 자체가 묶인다**는 점이다.

### 2. 스레드가 비싼 진짜 이유
- **스택 메모리**: JVM 기본 스레드 스택은 약 1MB. 스레드 1만 개면 **스택만 10GB**.
- **커널 객체 오버헤드**: OS는 각 스레드마다 `task_struct` 등 커널 자료구조를 유지한다.
- **컨텍스트 스위칭 비용**: 일반적으로 **1~10μs** 수준이며, 스위칭이 빈번해질수록 캐시 미스로 인한 간접 비용이 더 크다(L1/L2 캐시 워밍업 손실).
- **스케줄러 오버헤드**: 스레드 수가 늘수록 스케줄러의 결정 비용이 비선형적으로 증가한다.

즉, 스레드는 "비싼 자원"인데 그 비용을 I/O 대기에 묶어두는 것이 비효율의 핵심이다.

### 3. 두 해결책의 본질적 차이
**경량 스레드 (가상 스레드, 고루틴, 코루틴)**

- 동기 코드 스타일을 유지하면서 런타임이 스케줄링을 가져간다.
- 내부적으로는 결국 논블로킹 I/O를 사용한다(JVM 가상 스레드는 `epoll`/`kqueue` 위에서 동작).
- **개발자 경험 우선**: `read()`를 호출하면 그냥 결과를 받는 것처럼 보이고, 런타임이 블로킹 지점에서 캐리어 스레드를 다른 가상 스레드에 양보한다.

**논블로킹/비동기 I/O (Reactor, Promise/Future, async-await)**

- I/O 호출이 즉시 반환되고, 완료는 콜백/이벤트로 통보된다.
- 적은 수의 OS 스레드(보통 CPU 코어 수)로 수만 개의 커넥션을 처리한다.
- **자원 효율 우선**: 대신 코드가 콜백 체인이나 리액티브 스트림으로 변형되어 디버깅과 가독성 비용이 발생한다.

결론적으로, **둘은 대립이 아니라 동일한 OS 메커니즘(epoll/kqueue/IOCP)을 어떻게 추상화하느냐의 차이**다.

### 4. 사용자의 기술 스택별 매핑

|스택|경량 스레드 접근|논블로킹/비동기 접근|
|---|---|---|
|Spring Boot (Kotlin)|Virtual Thread (Java 21+), Kotlin Coroutine|WebFlux (Reactor)|
|Nest.js (TS)|(없음, V8은 단일 스레드)|`async/await` (Node.js의 libuv 이벤트 루프)|
|C# (Unity)|—|`async/await` (Task 기반)|

### 5. 빠진 관점: CPU-bound와 I/O-bound 구분
이 챕터가 강조하는 모든 최적화는 **I/O-bound 작업**에 한정된다. CPU-bound 작업(이미지 인코딩, 암호화, 무거운 계산)에서는 가상 스레드든 async/await든 도움이 되지 않는다. 오히려 단일 이벤트 루프를 막아버려 더 나쁘다. 이 경우엔 별도 워커 스레드 풀이나 프로세스 분리가 답이다.

게임 서버 관점에서 보면 Cibus Odyssey 같은 실시간 VR 서비스에서는 매치메이킹·세션 관리는 I/O-bound, 물리 시뮬레이션·리플리케이션은 CPU-bound로 명확히 갈리므로 이 구분이 실무에서 바로 필요한 판단이다.

## 한 줄 정리
> **스레드를 더 만드는 것**으로 풀려던 문제를, **스레드가 I/O에 묶이지 않게 하는 것**으로 푸는 패러다임 전환. 그 구현이 경량 스레드(코드 스타일 보존)와 논블로킹 I/O(자원 효율 극대화) 두 갈래로 나뉜다.
