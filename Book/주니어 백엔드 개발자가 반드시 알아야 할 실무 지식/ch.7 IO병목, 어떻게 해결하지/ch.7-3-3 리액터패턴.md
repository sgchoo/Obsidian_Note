# 리액터 패턴과 Node.js 이벤트 루프 정리

## 1. 리액터 패턴이란?

리액터 패턴은 동시에 들어오는 여러 이벤트를 효율적으로 처리하기 위한 이벤트 처리 패턴이다.

주로 네트워크 서버처럼 여러 클라이언트의 요청을 동시에 처리해야 하는 상황에서 사용된다.

리액터 패턴은 기본적으로 다음 흐름으로 동작한다.

```text
여러 이벤트 발생
  ↓
리액터가 이벤트 발생 여부를 감시
  ↓
이벤트가 준비되면 알맞은 핸들러에게 전달
  ↓
핸들러가 실제 작업 수행
  ↓
다시 이벤트 감시
````

---

## 2. 리액터 패턴의 주요 구성 요소

리액터 패턴은 크게 다음 요소로 구성된다.

```text
Reactor
Handler
Event
Demultiplexer
```

### Reactor

리액터는 이벤트가 발생할 때까지 대기하다가,  
이벤트가 발생하면 알맞은 핸들러에게 이벤트를 전달하는 역할을 한다.

즉, 직접 비즈니스 로직을 처리하기보다는  
**이벤트 감시와 이벤트 분배**를 담당한다.

```text
이벤트 감시
  ↓
이벤트 확인
  ↓
적절한 핸들러 호출
```

그래서 리액터는 보통 **이벤트 루프**라고도 볼 수 있다.

---

### Handler

핸들러는 실제 이벤트를 처리하는 코드이다.

예를 들어 다음과 같은 작업이 핸들러에 해당한다.

```text
클라이언트 요청 처리
파일 읽기 완료 후 처리
타이머 완료 후 실행
DB 응답 처리
네트워크 응답 처리
```

Node.js로 보면 우리가 작성하는 콜백 함수나 이벤트 리스너가 핸들러에 가깝다.

```js
server.on("request", (req, res) => {
  res.end("hello");
});
```

여기서 `(req, res) => { ... }` 부분이 요청 이벤트를 처리하는 핸들러라고 볼 수 있다.

---

### Event

이벤트는 처리해야 할 작업이 발생했다는 신호이다.

예를 들면 다음과 같다.

```text
클라이언트 연결 요청
데이터 수신
파일 읽기 완료
타이머 만료
소켓 쓰기 가능
```

---

### Demultiplexer

Demultiplexer는 여러 I/O 이벤트 중에서  
현재 어떤 이벤트가 처리 가능한 상태인지 골라내는 역할을 한다.

운영체제 수준에서는 다음과 같은 기능들이 여기에 해당한다.

```text
select
poll
epoll
kqueue
IOCP
```

즉, 많은 소켓이나 파일 디스크립터 중에서  
“지금 읽을 수 있는 것”, “지금 쓸 수 있는 것”, “이벤트가 발생한 것”을 찾아낸다.

리액터는 이 Demultiplexer를 통해 준비된 이벤트를 확인하고,  
그 이벤트를 적절한 핸들러에게 전달한다.

---

## 3. 리액터 패턴의 전체 흐름

리액터 패턴의 동작을 조금 더 자세히 쓰면 다음과 같다.

```text
1. 애플리케이션이 이벤트와 핸들러를 리액터에 등록한다.

2. 리액터는 이벤트가 발생할 때까지 대기한다.

3. 운영체제 또는 I/O Demultiplexer가 준비된 이벤트를 알려준다.

4. 리액터는 준비된 이벤트를 확인한다.

5. 리액터는 해당 이벤트에 등록된 핸들러를 호출한다.

6. 핸들러는 실제 작업을 수행한다.

7. 처리가 끝나면 리액터는 다시 이벤트 대기 상태로 돌아간다.
```

이를 간단히 표현하면 다음과 같다.

```text
등록된 이벤트들
  ↓
Reactor
  ↓
I/O 이벤트 감시
  ↓
준비된 이벤트 확인
  ↓
Handler 실행
  ↓
다시 이벤트 감시
```

---

## 4. 리액터 패턴과 논블로킹 I/O

리액터 패턴은 보통 논블로킹 I/O와 함께 사용된다.

블로킹 I/O에서는 작업이 끝날 때까지 스레드가 대기한다.

```text
요청 수신
  ↓
파일 읽기 시작
  ↓
파일 읽기 완료까지 스레드 대기
  ↓
다음 작업 처리
```

반면 논블로킹 I/O에서는 작업을 요청한 뒤,  
완료될 때까지 스레드가 막혀 있지 않는다.

```text
요청 수신
  ↓
파일 읽기 요청
  ↓
스레드는 다른 이벤트 처리
  ↓
파일 읽기 완료 이벤트 발생
  ↓
핸들러 실행
```

즉, 리액터 패턴은 다음 구조를 가능하게 한다.

```text
하나의 스레드 또는 적은 수의 스레드로
여러 I/O 이벤트를 번갈아가며 처리한다.
```

---

## 5. 리액터 패턴의 장점

리액터 패턴의 장점은 다음과 같다.

```text
스레드를 요청마다 만들지 않아도 된다.
적은 수의 스레드로 많은 연결을 처리할 수 있다.
I/O 대기 시간 동안 스레드가 낭비되지 않는다.
이벤트 중심으로 서버를 구성할 수 있다.
```

예를 들어 요청마다 스레드를 만드는 방식은 다음과 같다.

```text
요청 A → 스레드 A
요청 B → 스레드 B
요청 C → 스레드 C
요청 D → 스레드 D
```

요청이 많아질수록 스레드 수도 많아진다.

반면 리액터 패턴은 다음과 같이 처리할 수 있다.

```text
요청 A
요청 B
요청 C
요청 D
   ↓
하나의 이벤트 루프가 준비된 이벤트만 골라 처리
```

---

## 6. 리액터 패턴의 한계

리액터 패턴의 중요한 한계는  
핸들러가 오래 실행되면 전체 이벤트 처리가 지연된다는 점이다.

리액터는 이벤트를 감시하고,  
준비된 이벤트에 맞는 핸들러를 호출한다.

그런데 핸들러 안에서 오래 걸리는 작업을 수행하면,  
리액터는 그 작업이 끝날 때까지 다음 이벤트를 처리하지 못한다.

```text
이벤트 A 발생
  ↓
Handler A 실행
  ↓
Handler A에서 오래 걸리는 CPU 연산 수행
  ↓
그동안 이벤트 B, C, D 처리 지연
```

따라서 리액터 패턴에서는 핸들러가 가볍고 빠르게 끝나는 것이 중요하다.

---

## 7. 핸들러에서 피해야 할 작업

리액터 패턴에서 핸들러 내부에 다음 작업이 들어가면 문제가 될 수 있다.

```text
오래 걸리는 CPU 연산
동기 파일 I/O
동기 네트워크 I/O
동기 DB 호출
큰 데이터 압축/해제
복잡한 암호화 연산
```

이런 작업은 이벤트 루프를 막을 수 있다.

따라서 무거운 작업은 별도의 스레드 풀, 워커 스레드, 작업 큐 등으로 분리하는 것이 좋다.

---

## 8. Node.js 이벤트 루프와 리액터 패턴

Node.js의 이벤트 루프는 리액터 패턴과 유사한 방식으로 동작한다.

Node.js는 네트워크 요청, 타이머, 파일 I/O 완료 같은 이벤트를 감시하다가,  
이벤트가 준비되면 해당 콜백 함수를 실행한다.

```text
클라이언트 요청
파일 I/O 완료
타이머 만료
네트워크 응답
  ↓
Node.js 이벤트 루프
  ↓
등록된 콜백 실행
```

Node.js에서 우리가 작성하는 콜백 함수는 리액터 패턴의 핸들러와 비슷하다.

```js
setTimeout(() => {
  console.log("타이머 완료");
}, 1000);
```

여기서 `() => { ... }` 부분이 타이머 이벤트에 대한 핸들러라고 볼 수 있다.

---

## 9. Node.js 내부 구조와 libuv

Node.js의 이벤트 루프는 libuv라는 라이브러리를 기반으로 동작한다.

libuv는 운영체제의 비동기 I/O 기능을 감싸서,  
Node.js가 플랫폼에 상관없이 이벤트 루프 기반으로 동작할 수 있게 해준다.

```text
JavaScript 코드
  ↓
Node.js API
  ↓
libuv
  ↓
운영체제의 비동기 I/O 또는 스레드 풀
  ↓
작업 완료 이벤트
  ↓
이벤트 루프
  ↓
콜백 실행
```

즉, Node.js의 이벤트 루프는 리액터 패턴의 개념을 실제 런타임 수준에서 구현한 구조로 이해할 수 있다.

---

## 10. Node.js에서 이벤트 루프를 막는 코드

Node.js는 비동기 이벤트 기반 런타임이지만,  
JavaScript 콜백 자체는 이벤트 루프 위에서 실행된다.

따라서 콜백 안에서 오래 걸리는 CPU 연산을 하면 이벤트 루프가 막힌다.

```js
function heavyCalculation() {
  let i;

  for (i = 0; i < 10_000_000_000; i++) {}

  return i;
}

server.on("request", (req, res) => {
  const result = heavyCalculation();

  res.end(String(result));
});
```

이 코드에서는 요청 핸들러 안에서 무거운 CPU 연산을 수행한다.

그 결과 `heavyCalculation()`이 끝날 때까지 다른 요청, 타이머, I/O 콜백 처리가 지연된다.

---

## 11. libuv Worker Pool

Node.js는 일부 무거운 작업을 이벤트 루프가 직접 처리하지 않고,  
libuv의 Worker Pool에 위임한다.

대표적으로 다음 작업들이 여기에 해당한다.

```text
비동기 파일 I/O
일부 DNS 작업
crypto 연산
zlib 압축/해제 작업
```

예를 들면 다음 API들은 내부적으로 Worker Pool을 사용할 수 있다.

```js
fs.readFile(...)
dns.lookup(...)
crypto.pbkdf2(...)
zlib.deflate(...)
```

이 구조를 통해 Node.js는 이벤트 루프가 직접 블로킹되지 않도록 일부 작업을 분리한다.

하지만 중요한 점은  
사용자가 직접 작성한 JavaScript CPU 연산은 자동으로 Worker Pool에서 실행되지 않는다는 것이다.

---

## 12. 직접 작성한 CPU 연산은 Worker Thread로 분리해야 한다

다음 함수는 자동으로 libuv Worker Pool에서 실행되지 않는다.

```js
function heavyCalculation() {
  let i;

  for (i = 0; i < 10_000_000_000; i++) {}

  return i;
}
```

이런 직접 작성한 CPU 연산은 이벤트 루프 위에서 실행된다.

따라서 무거운 계산을 분리하려면 `worker_threads`를 사용할 수 있다.

```text
메인 스레드
  ↓
Worker Thread 생성
  ↓
무거운 계산 요청
  ↓
Worker Thread에서 계산 수행
  ↓
결과를 메인 스레드로 전달
```

이렇게 하면 메인 이벤트 루프가 무거운 CPU 연산에 의해 막히는 문제를 줄일 수 있다.

---

## 13. Worker Thread 작업은 비동기 결과로 받아야 한다

Worker Thread는 메인 스레드와 별도로 실행되기 때문에,  
결과를 바로 동기적으로 받을 수 없다.

잘못 이해하기 쉬운 예시는 다음과 같다.

```js
async function heavyFunc() {
  const worker = new WorkerThread();

  const temp = worker.heavyCalculation();

  console.log(temp);
}

await heavyFunc();
```

여기서 `worker.heavyCalculation()`이 비동기 작업이라면  
`temp`에는 실제 계산 결과가 바로 들어오지 않는다.

보통은 다음과 같은 상태일 수 있다.

```js
Promise { <pending> }
```

따라서 결과가 필요하다면 내부에서도 `await`를 해야 한다.

```js
async function heavyFunc() {
  const temp = await runHeavyCalculationInWorker();

  console.log(temp);

  return temp;
}

const result = await heavyFunc();
```

---

## 14. await의 의미

`await`는 이벤트 루프 전체를 멈추는 것이 아니다.

`await`는 현재 async 함수의 실행을 잠시 중단하고,  
기다리던 Promise가 완료되면 그 다음 줄부터 다시 실행하게 한다.

```js
const temp = await runHeavyCalculationInWorker();
```

이 코드는 다음 의미이다.

```text
Worker Thread의 계산 결과가 올 때까지
heavyFunc 함수의 나머지 실행을 잠시 멈춘다.

하지만 그동안 이벤트 루프는 다른 이벤트를 처리할 수 있다.
```

---

## 15. 최종 정리

리액터 패턴은 여러 이벤트를 감시하다가,  
준비된 이벤트를 알맞은 핸들러에게 전달하는 이벤트 처리 패턴이다.

Node.js의 이벤트 루프는 이 리액터 패턴과 유사하게 동작한다.

Node.js는 이벤트 루프를 통해 여러 I/O 이벤트를 처리하고,  
이벤트가 준비되면 등록된 콜백 함수를 실행한다.

하지만 콜백 핸들러는 이벤트 루프 위에서 실행되기 때문에,  
핸들러 안에서 오래 걸리는 CPU 연산이나 블로킹 작업을 수행하면 전체 이벤트 처리가 지연된다.

Node.js는 이를 보완하기 위해 일부 파일 I/O, DNS, crypto, zlib 작업을 libuv Worker Pool에 위임한다.

하지만 사용자가 직접 작성한 JavaScript CPU 연산은 자동으로 Worker Pool에서 실행되지 않는다.

따라서 직접 작성한 무거운 CPU 연산은 Worker Thread, child_process, 별도 작업 서버, 메시지 큐 등을 사용해 이벤트 루프와 분리해야 한다.

그리고 Worker Thread 작업은 비동기적으로 결과를 돌려주기 때문에,  
그 결과를 실제 값으로 사용하려면 await로 기다려야 한다.

---

## 한 줄 요약

리액터 패턴은 이벤트를 감시하고 준비된 이벤트를 핸들러에 전달하는 구조이며,  
Node.js 이벤트 루프는 이와 유사하게 동작한다.  
다만 핸들러에서 무거운 CPU 연산을 수행하면 이벤트 루프가 막히므로,  
이런 작업은 Worker Thread나 별도 실행 흐름으로 분리해야 한다.
