# 2-2. 서버 성능 개선 기초

## 1. 스케일링 전략

### 긴급 대응 방안

- 긴급하게 개선이 필요한 경우 **Scale-up**을 통해 응답시간↓, 처리량↑
- 하지만 수직확장은 비용이 많이 들어가므로 **Scale-out**을 통해 TPS를 높이는 방법도 고려 필요

### ⚠️ 주의사항

> DB에 문제가 있는 상황에서 서버를 추가하면 불에 기름을 붓는 격  
> → 정확한 원인 파악 필요

## 2. DB 커넥션 관리

### 2.1 커넥션 풀의 필요성

- 다이렉트로 연결할 시 DB를 연결하고 해제하는 시간이 **0.5초~1초**로 매우 길다
- 따라서 커넥션 풀 사용이 필수

### 2.2 커넥션 풀 주요 설정

#### 1) 커넥션 풀 크기

- 커넥션 풀 크기를 확장시켜 응답시간을 줄일 수 있음
- 단, DB 서버 상태를 고려하여 적절한 크기를 유지해야 함

#### 2) 대기시간 설정

- 풀에 커넥션이 없을 때, 커넥션을 구할 때까지 대기시간
- 대기 시간은 짧게 가져간 후, 에러 응답을 빨리 보내는 것이 유리
- UX, 서버 성능 등의 측면에서 중요

#### 3) 커넥션 유지 시간

- 최대 유휴시간
- 최대 유지 시간

### 2.3 DB 연결 관리

#### 자동 연결 해제

- DB는 일정 시간 동안 상호작용이 없으면 자동으로 연결을 끊는 기능 제공
- 모든 유휴시간이 지난 커넥션을 사용하려 할 때 에러 발생

#### 에러 방지 방법

DB는 다음 기능들을 제공:

- **최대 유휴시간 설정**
- **유효성 검사 지원**

#### 커넥션 처리 프로세스

```
풀에서 커넥션 확인 → 유효성 확인 → 사용 가능 커넥션 없음 확인 → 재생성 → DB 쿼리
```

## 3. 캐시 활용

### 3.1 캐시의 효율성

- DB의 처리량 증대를 위해 Scale up/out보다 **캐시를 활용하는 것이 효율적**일 수 있음

### 3.2 캐시 종류

|종류|특징|장점|단점|
|---|---|---|---|
|**로컬 캐시**|서버 내부 메모리 사용|빠른 응답 속도|서버별 독립 관리, 일관성 문제|
|**리모트 캐시**|Redis 등 외부 캐시 서버|데이터 공유 가능, 일관성 유지|네트워크 오버헤드|

> 각기 장단점이 뚜렷하기에 용도에 맞게 사용해야 함

### 3.3 캐시 활용 전략

- 변경되지 않을 법한 데이터를 사전에 적재
- 갑작스럽게 "조회" 요청이 증가하여도 안정적으로 운영 가능

### 3.4 캐시 관리 핵심

> 🔴 **중요**: 캐시를 사용할 때 반드시 신경써야 하는 것은 **적절한 시점에 캐시를 삭제**하는 것

### 📊 성능 개선 우선순위

1. **원인 파악** - DB 문제인지 서버 문제인지 확인
2. **캐시 도입** - 가장 비용 효율적
3. **커넥션 풀 최적화** - 설정 조정으로 개선
4. **Scale-out** - 수평 확장
5. **Scale-up** - 수직 확장 (비용 높음)
