# 📝 5장. 비동기 연동, 언제 어떻게 써야할까?

## 1. 동기(Synchronous) vs 비동기(Asynchronous) 연동: 커피숍 비유 ☕

백엔드 개발에서 동기와 비동기의 차이를 이해하는 것은 매우 중요합니다. 커피숍에 가서 주문하는 상황을 떠올려보면 쉽게 이해할 수 있습니다.

- **📞 동기 (Synchronous): "기다리세요, 손님!"**
    
    - **상황:** 키오스크가 없는 옛날 카페. 당신은 카운터에서 커피를 주문하고, 바리스타가 커피를 만드는 동안 **그 자리에서 계속 기다립니다.** 커피가 나와야만 자리에 가서 앉을 수 있습니다.
        
    - **특징:**
        
        - **흐름이 직관적:** 주문 -> 대기 -> 수령. 순서가 명확하고 이해하기 쉽습니다.
            
        - **디버깅 용이:** 문제가 생기면 어느 단계에서 멈췄는지 바로 알 수 있습니다.
            
    - **한계:** 내 커피가 만들어지는 동안 나는 아무것도 못 하고 **'대기(Blocking)'** 해야 합니다. 바리스타가 원두를 가는 데 5분이 걸린다면, 나도 5분을 꼼짝없이 기다려야 합니다.
        
- **📲 비동기 (Asynchronous): "진동벨 울리면 오세요!"**
    
    - **상황:** 요즘 흔히 볼 수 있는 카페. 당신은 주문 후 **진동벨**을 받습니다. 그리고 자리에 가서 앉아 책을 보거나 친구와 대화하는 등 다른 일을 할 수 있습니다. 진동벨이 울리면 그때 커피를 받으러 갑니다.
        
    - **특징:**
        
        - **효율적인 시간 사용:** 커피가 만들어지는 동안 다른 작업을 할 수 있어 **'대기(Blocking)' 상태가 발생하지 않습니다.**
            
        - **더 나은 사용자 경험:** 주문자는 즉시 다른 행동을 할 수 있어 기다림의 지루함이 없습니다.
            
    - **한계:** 주문한 커피가 정확히 언제 나올지 예측하기는 조금 더 어렵습니다.

## 2. 동기 연동의 함정: 외부 서비스 연동

우리가 개발하는 서비스는 종종 이메일 발송, 결제, 소셜 로그인 등 외부 서비스와 연동됩니다. 이때 동기 방식은 몇 가지 심각한 문제를 일으킬 수 있습니다.

- **문제 1: 외부 서비스의 장애가 내 서비스의 장애로 이어진다.**
    
    - **상황:** 사용자가 회원가입을 합니다. `[DB에 유저 저장 (성공)]` -> `[환영 이메일 발송 (시도)]` 순서로 동작한다고 가정해 봅시다.
        
    - 만약 이메일 발송 서버가 다운되어 응답이 없다면, 동기 방식에서는 전체 회원가입 프로세스가 **멈춰버립니다.** 결국 사용자는 "회원가입 실패" 메시지를 보게 됩니다.
        
    - **고민할 점:** "이메일 발송 실패가 회원가입 전체를 실패시킬 만큼 치명적인가?" (대부분의 경우, 그렇지 않습니다.)
        
- **문제 2: 외부 서비스의 느린 응답이 내 서비스의 성능을 저하시킨다.**
    
    - **상황:** 이메일 발송에 5초가 걸린다고 가정해 봅시다.
        
    - 동기 방식에서는 사용자가 '가입하기' 버튼을 누른 후, 이메일 발송이 완료될 때까지 **5초 동안 로딩 화면만 봐야 합니다.** 이는 매우 나쁜 사용자 경험(UX)을 유발합니다.
        

> **핵심:** "다음 작업을 진행하기 위해 **반드시** 외부 연동 결과가 필요한가?" 이 질문에 "아니오"라고 답할 수 있다면, 비동기 연동을 적극적으로 고려해야 합니다.

## 3. 비동기 연동은 언제 사용해야 할까?

사용자에게 "요청 접수 완료!"라고 즉시 알려주고, 시간이 걸리는 작업은 백그라운드에서 처리해도 괜찮은 기능들에 비동기 방식이 적합합니다.

- **연동에 약간의 시차가 생겨도 괜찮은 기능**
    
    - **예시:** 회원가입 환영 이메일, 앱 푸시 알림, 게시물 등록 시 팔로워에게 알림 발송 등
        
    - 이메일이나 알림이 1~2초 늦게 도착한다고 해서 서비스의 핵심 기능에 문제가 생기지는 않습니다.
        
- **실패 시 재시도가 필요한 기능**
    
    - **예시:** 외부 결제 API 호출, 사내 어드민 시스템에 데이터 전송 등
        
    - 네트워크 문제 등으로 외부 API 호출이 일시적으로 실패했을 때, 동기 방식에서는 즉시 에러가 발생하지만 비동기 방식에서는 **몇 초 뒤에 자동으로 재시도**하도록 구현할 수 있습니다.
        
- **실패 시 수동 처리가 가능한 기능**
    
    - **예시:** 사용자 통계 데이터 집계, 어드민 로그 기록 등
        
    - 자동 처리에 실패하더라도, 나중에 개발자가 실패 기록(로그)을 보고 수동으로 복구할 수 있는 작업들입니다.
        
- **실패해도 무시할 수 있는 기능**
    
    - **예시:** 사용자 행동 로그 수집, 추천 데이터 생성 등
        
    - 일부 로그가 유실되더라도 전체 서비스 운영에 치명적이지 않은 경우에 해당합니다.
