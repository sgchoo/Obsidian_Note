# 5-3. 메시징 시스템 (Messaging System)

메시징 시스템은 시스템 간의 데이터 교환을 **비동기 방식**으로 처리하여, 전체 시스템의 유연성과 안정성을 높이는 중요한 아키텍처 패턴입니다.

## 📌 1. 메시징 시스템의 기본 구조

메시징 시스템의 가장 기본적인 흐름은 다음과 같습니다.

1. **생산자 (Producer/Publisher):** 시스템 A는 전달할 데이터를 **메시지(Message)** 형태로 변환하여 **메시징 시스템(Message Broker)**으로 전송합니다.
    
2. **메시지 브로커 (Message Broker):** 메시지를 **큐(Queue)** 또는 **토픽(Topic)**이라는 공간에 안전하게 저장합니다. 대표적인 브로커로는 **Kafka, RabbitMQ** 등이 있습니다.
    
3. **소비자 (Consumer/Subscriber):** 시스템 B는 메시지 브로커로부터 메시지를 가져와(소비하여) 필요한 작업을 처리합니다.
    

코드 스니펫

```
graph TD
    A[시스템 A (Producer)] -- 메시지 전송 --> B((메시지 브로커));
    B -- 메시지 전달 --> C[시스템 B (Consumer)];
```

> 💡 **핵심:** 시스템 A와 B는 서로를 직접 호출하는 것이 아니라, 메시지 브로커라는 '중간 다리'를 통해 통신합니다. 이로 인해 두 시스템은 서로의 상태에 의존하지 않게 됩니다.

---

## 🚀 2. 메시징 시스템 도입의 장점

직접 통신하는 방식보다 구조가 복잡해지지만, 다음과 같은 강력한 이점을 얻을 수 있습니다.

- **시스템 간 결합도 감소 (Decoupling):**
    
    - 메시지 브로커가 중간에서 버퍼 역할을 하므로, 한쪽 시스템에 장애가 발생하거나 바쁘더라도 다른 시스템에 직접적인 영향을 주지 않습니다.
        
    - 예를 들어, 시스템 B가 일시적으로 다운되어도 시스템 A는 정상적으로 메시지를 브로커에 보내고 자신의 작업을 계속할 수 있습니다. 시스템 B는 복구된 후에 밀려있던 메시지를 처리하면 됩니다.
        
- **유연한 확장성 (Scalability):**
    
    - 처리량이 늘어났을 때, 작업이 필요한 소비자(시스템)만 독립적으로 확장(Scale-out)할 수 있습니다.
        
    - 또한, 메시지를 받아 처리해야 할 새로운 시스템 C, D가 생긴다면, 브로커에 새로운 소비자를 연결하기만 하면 되므로 기존 로직을 수정할 필요가 없습니다.

## 🛠️ 3. 대표적인 메시징 기술

어떤 기술을 선택할지는 시스템의 요구사항(데이터 처리량, 안정성, 기능 등)에 따라 달라집니다.

|기술 스택|특징|주로 사용되는 경우|
|---|---|---|
|**Apache Kafka**|대용량, 고성능의 실시간 데이터 스트리밍에 특화되어 있습니다. 분산 시스템으로 설계되어 확장성과 장애 복구 능력이 뛰어납니다.|로그 수집, 실시간 분석, 이벤트 스트리밍 등 대규모 트래픽 처리|
|**RabbitMQ**|AMQP라는 표준 프로토콜을 구현한 메시지 브로커입니다. 유연한 라우팅 옵션과 다양한 메시징 패턴을 제공하며, 안정성이 높습니다.|신뢰성이 중요한 업무 처리, 다양한 라우팅 규칙이 필요한 시스템|
|**Redis Pub/Sub**|In-memory 데이터 저장소인 Redis의 발행/구독 기능을 이용한 방식입니다. 매우 빠르지만, 데이터 영속성을 보장하지 않아 메시지 유실의 위험이 있습니다.|실시간 채팅, 알림, 간단한 이벤트 전파 등 속도가 중요하고 메시지 유실이 치명적이지 않은 경우|

## ⚠️ 4. 메시지 처리 시 고려사항

메시징 시스템을 안정적으로 운영하기 위해서는 장애 상황을 반드시 고려해야 합니다.

### 4-1. 메시지 유실 방지

메시지는 중요한 데이터이므로 유실되지 않도록 보장해야 합니다. 생산자가 메시지를 보냈지만 브로커에 도달하지 못하거나, 소비자가 메시지를 처리하기 전에 장애가 발생하는 상황을 대비해야 합니다.

**대응 방안:**

- **ACK (Acknowledgement) 메커니즘 활용:** 소비자가 메시지를 성공적으로 처리한 후에 브로커에 **"처리 완료" 신호(ACK)**를 보냅니다. 만약 브ро커가 일정 시간 동안 ACK를 받지 못하면, 해당 메시지를 다른 소비자에게 다시 전달합니다.
    
- **생산자 확인 (Publisher Confirms):** 생산자가 보낸 메시지가 브로커에 안전하게 저장되었는지 확인하는 콜백을 받습니다.
    

### 4-2. 메시지 중복 처리와 멱등성(Idempotency)

네트워크 문제나 ACK 실패 등으로 인해 **소비자는 동일한 메시지를 여러 번 받을 수 있습니다.** 이는 의도치 않은 결과를 초래할 수 있습니다. (예: 결제 요청 메시지가 중복 처리되어 이중 결제 발생)

**원인:**

1. **생산자의 재전송:** 생산자가 메시지를 보낸 후, 브로커로부터 응답을 받지 못해 타임아웃이 발생하면 같은 메시지를 다시 보낼 수 있습니다.
    
2. **소비자의 재수신:** 소비자가 메시지를 처리했지만, 처리 완료 신호(ACK)를 보내기 전에 장애가 발생하면 브로커는 해당 메시지를 다른 소비자에게 다시 전달합니다.
    

**대응 방안:**

- **메시지에 고유 ID 부여:** 모든 메시지에 유니크한 ID를 부여하고, 소비자는 이 ID를 기록하여 이미 처리한 메시지인지 확인하는 로직을 추가합니다. (예: 처리 완료된 메시지 ID를 DB나 Redis에 저장)
    
- **API의 멱등성 확보:** 동일한 요청을 여러 번 보내더라도 **항상 같은 결과**가 나오도록 API를 설계합니다. 예를 들어, '주문 생성'이 아닌 '특정 ID의 주문을 생성 또는 업데이트'하는 방식으로 API를 구현하면 여러 번 호출되어도 문제가 발생하지 않습니다.
    

### 4-3. 처리 실패 시 정책

메시지 소비 과정에서 예외(네트워크 오류, 데이터 형식 불일치 등)가 발생했을 때 어떻게 처리할지 정책을 정해야 합니다.

- **무시 (Ignore):** 중요하지 않은 메시지라면 무시하고 넘어갈 수 있습니다.
    
- **재시도 (Retry):** 일시적인 오류일 수 있으므로, 몇 차례 더 재시도합니다. 단, 무한정 재시도하면 시스템에 부하를 줄 수 있으므로 재시도 횟수 제한과 간격(Back-off) 설정이 중요합니다.
    
- **실패 처리 및 로깅 (Dead Letter Queue):** 계속해서 실패하는 메시지는 별도의 **'데드 레터 큐(DLQ)'**로 보내고, 개발자가 원인을 분석할 수 있도록 실패 로그를 상세히 남깁니다.

## 📚 5. 메시지의 두 가지 유형

메시지는 목적에 따라 크게 두 가지로 나눌 수 있습니다.

- **이벤트 (Event):** "어떤 일이 발생했음"을 알리는 메시지입니다. (과거형)
    
    - 예: `주문이_완료되었다 (OrderCompleted)`, `회원이_가입했다 (UserSignedUp)`
        
    - 이벤트를 발행하는 쪽은 누가 이 메시지를 받아서 처리할지 신경 쓰지 않습니다.
        
- **커맨드 (Command):** "무엇을 해달라"고 요청하는 메시지입니다. (명령형)
    
    - 예: `주문을_생성하라 (CreateOrder)`, `이메일을_발송하라 (SendEmail)`
        
    - 커맨드는 보통 특정 소비자(시스템)가 처리하도록 의도된 경우가 많습니다.
