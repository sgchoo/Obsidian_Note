# 서버 트래픽 처리 능력 측정 가이드

## 1. 왜 실제 측정이 필요한가

서버가 감당할 수 있는 트래픽 규모는 이론적으로 예측하기 어렵다. CPU/메모리 스펙, 코드 구조, DB 커넥션 풀 설정, 네트워크 대역폭 등 여러 요소가 복합적으로 작용하기 때문에, 실제 부하를 걸어 관찰하는 것이 유일하게 신뢰할 수 있는 방법이다. 이를 통해 다음을 파악할 수 있다.

- 현재 인프라로 감당 가능한 최대 동시 사용자 수 / RPS(Requests Per Second)
- 병목 구간 (DB, 네트워크 I/O, 특정 API 로직, GC 등)
- 장애가 발생하는 임계점과 그 시점의 증상
- 오토스케일링/캐싱/큐잉 등 개선 조치의 효과 검증

---

## 2. 핵심 측정 지표

### 2.1 응답 시간 (Latency / Response Time)

요청을 보낸 시점부터 응답을 받기까지 걸리는 시간.

- **평균(Average)**: 전체 경향 파악에는 유용하지만 이상치에 왜곡되기 쉬움
- **백분위수(Percentile)**: 실무에서 가장 중요하게 보는 지표
    - `p50`(중앙값): 일반적인 사용자 경험
    - `p95`, `p99`: 느린 요청, 즉 사용자 불만으로 이어질 가능성이 높은 구간
    - `p99.9`: 대규모 트래픽에서 SLA 위반 여부 판단에 사용
- 평균만 보고 "빠르다"고 판단하면 안 되고, 반드시 p95/p99를 함께 확인해야 함

### 2.2 처리량 (Throughput)

단위 시간당 처리 가능한 요청 수.

- **RPS/TPS** (Requests/Transactions Per Second)로 표현
- 처리량은 응답 시간과 트레이드오프 관계에 있는 경우가 많음 (동시 요청이 늘면 응답 시간이 늘어나며 처리량 상승이 둔화됨)
- **최대 처리량(Max Throughput)**과 **적정 처리량(Sustainable Throughput, 응답 시간 SLA를 만족하는 선에서의 처리량)**을 구분해서 봐야 함

### 2.3 자원 사용량 (Resource Utilization)

서버 및 인프라 구성 요소의 부하 상태.

- **CPU 사용률**: 특정 로직(직렬화, 암호화, 정규식 등)의 병목 여부 확인
- **메모리 사용률 / GC 빈도**: JVM(Kotlin/Spring) 환경에서는 GC pause가 응답 시간 스파이크의 원인이 되는 경우가 많음
- **네트워크 I/O**: 대역폭 포화, 커넥션 수 한계
- **DB 커넥션 풀 / 쿼리 응답 시간**: 대부분의 병목이 실제로는 DB 레이어에서 발생
- **에러율(Error Rate)**: 4xx/5xx 비율, 타임아웃, 커넥션 리셋 등

> 위 지표들은 개별적으로 보지 않고 **"트래픽 증가 → 응답 시간/에러율 변화 → 어느 자원이 먼저 포화되는가"**의 상관관계로 함께 분석해야 실제 병목을 특정할 수 있다.

## 3. 테스트 종류

### 3.1 부하 테스트 (Load Testing)

**목적**: 예상되는 정상 ~ 목표 트래픽 수준에서 시스템이 안정적으로 동작하는지 확인

- 실제 운영 환경에서 예상되는 동시 사용자 수 / RPS를 기준으로 점진적으로 부하를 증가시키며 진행
- 응답 시간, 처리량이 목표 SLA를 만족하는지 검증하는 것이 핵심
- 예: "동시 사용자 1,000명 기준으로 p95 응답 시간이 300ms 이내인가?"

### 3.2 스트레스 테스트 (Stress Testing)

**목적**: 시스템이 감당할 수 있는 한계를 찾고, 한계를 넘었을 때 어떻게 실패하는지(Failure Mode) 확인

- 정상 범위를 넘어서까지 부하를 계속 증가시켜 시스템이 무너지는 지점(Breaking Point)을 찾음
- 단순히 "언제 죽는가"뿐 아니라, "죽을 때 얼마나 우아하게(graceful) 실패하는가", "복구는 잘 되는가"도 중요한 관찰 포인트
- 예: 커넥션 풀 고갈 시 요청이 큐잉되는지, 즉시 에러를 반환하는지, 아니면 서버 전체가 다운되는지

### 3.3 지속 부하 테스트 (Soak Testing / Endurance Testing)

**목적**: 일정 수준의 부하를 장시간(수 시간~수 일) 지속했을 때 발생하는 문제 확인

- 순간적인 스파이크 테스트로는 발견되지 않는 문제를 잡아냄
- 대표적으로 찾아내는 문제:
    - 메모리 누수 (Memory Leak)
    - 커넥션/파일 디스크립터 누수
    - 디스크 사용량 지속 증가 (로그 적재 등)
    - GC 누적으로 인한 점진적 성능 저하
- 단기 부하 테스트에서는 "정상"으로 보이던 시스템이 장시간 운영 시 서서히 무너지는 케이스를 발견하는 데 필수적

### 3.4 스파이크 테스트 (Spike Testing)

**목적**: 트래픽이 급격히, 순간적으로 증가했을 때의 대응 능력 확인

- 이벤트/프로모션, 뉴스 노출 등으로 트래픽이 단시간에 수 배~수십 배 폭증하는 상황을 시뮬레이션
- 확인 포인트:
    - 오토스케일링이 트래픽 증가 속도를 따라가는가 (스케일 아웃 지연 시간)
    - 큐/캐시가 순간 부하를 얼마나 흡수하는가
    - 스파이크 이후 정상 수준으로 트래픽이 감소했을 때 시스템이 정상 복구되는가
- 지속 부하 테스트가 "천천히 무너지는지"를 본다면, 스파이크 테스트는 "급격한 변화에 즉각 버티는지"를 본다는 점에서 목적이 다름

## 4. 테스트 유형 비교

|구분|부하 강도 패턴|주요 확인 목적|
|---|---|---|
|부하 테스트|목표 트래픽까지 점진적 증가|정상 운영 조건에서의 SLA 충족 여부|
|스트레스 테스트|한계까지 지속 증가|최대 처리 한계 및 실패 양상|
|지속 부하 테스트|일정 부하를 장시간 유지|누수, 장기적 성능 저하|
|스파이크 테스트|순간적 급증 후 급감|트래픽 급변에 대한 대응력, 복구력|

---

## 5. 실무 진행 순서 제안

1. **목표 설정**: 예상 트래픽, SLA(응답 시간, 에러율 목표) 정의
2. **부하 테스트**로 목표 트래픽에서의 안정성 1차 검증
3. **스트레스 테스트**로 실제 한계치와 실패 양상 파악, 병목 지점 식별 및 개선
4. **스파이크 테스트**로 급격한 트래픽 변화 대응력 검증 (오토스케일링/캐시 정책 점검)
5. **지속 부하 테스트**로 장시간 운영 시의 안정성(메모리 누수 등) 최종 검증
6. 개선 후 회귀 테스트로 재검증 → 반복

## 6. 참고: 사용 가능한 도구

- **k6**: JS 기반 스크립트 작성, 결과 시각화 용이, 최근 실무에서 많이 사용
- **Apache JMeter**: GUI 기반, 다양한 프로토콜 지원, 러닝커브는 있지만 기능 풍부
- **Gatling**: Scala 기반이나 최근 Java DSL 지원, 상세한 리포트 제공
- **nGrinder**: 네이버에서 만든 도구, 분산 부하 테스트에 강점

Nest.js/Spring Boot 서버라면 k6로 시나리오를 작성하고, Prometheus + Grafana로 위 지표(응답 시간, 처리량, 자원 사용량)를 실시간 모니터링하며 테스트를 진행하는 조합이 일반적으로 무난하다.
