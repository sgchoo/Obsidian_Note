# 응답 시간(Response Time) 지표

성능 테스트에서 응답 시간은 가장 핵심적인 지표이지만, 단일 값만으로는 시스템의 실제 성능을 대표할 수 없다. 여러 통계값을 함께 확인해야 신뢰할 수 있는 해석이 가능하다.

## 1. 주요 측정값

|지표|설명|
|---|---|
|평균 (Mean)|전체 요청의 응답 시간 산술 평균|
|최대 (Max)|가장 느렸던 단일 요청의 응답 시간|
|최소 (Min)|가장 빨랐던 단일 요청의 응답 시간|
|중앙값 (Median, 50th Percentile)|전체 요청을 정렬했을 때 정확히 중간에 위치한 값|
|95th / 99th Percentile|전체 요청 중 95% / 99%가 이 값 이하로 응답했음을 의미|

## 2. 평균과 최대값의 괴리

평균과 최대값의 차이가 크다면, 일부 요청에서 극단적으로 느린 응답(outlier)이 존재한다는 의미다. 이때는 평균만으로 전체 사용자 경험을 판단할 수 없으므로 **95th / 99th 백분위수를 반드시 함께 확인**해야 한다.

- 백분위수는 소수의 이상치에 흔들리지 않고, 실제 다수 사용자가 체감하는 응답 시간을 파악하는 데 유용하다.
- 예: 평균 200ms인데 99th 백분위가 3000ms라면, 대부분은 빠르지만 1%의 사용자는 매우 느린 경험을 하고 있다는 뜻이다.

## 3. 중앙값과 평균값의 관계 (분포 해석) — 용어 정정

> 원문에서 "평균이 중앙값보다 크면 좌편향"이라고 되어 있었으나, 통계적으로는 반대다.

**평균값이 중앙값보다 크다면 이는 우편향(Right-skewed, Positively Skewed) 분포를 의미한다.**

- 대부분의 요청은 중앙값 부근에서 빠르게 처리되지만, 소수의 매우 느린 응답(꼬리, tail)이 평균을 중앙값보다 위로 끌어올리는 형태
- 반대로 평균 < 중앙값이면 좌편향(Left-skewed)이며, 이는 실무에서 드물게 나타남
- 즉, "평균이 중앙값보다 크다 = 꼬리가 오른쪽(느린 쪽)으로 길게 늘어져 있다 = 일부 요청이 비정상적으로 느리다"로 해석해야 한다

이런 경우 평균 수치가 양호하게 보여도 **tail latency(꼬리 지연) 문제**를 의심해야 한다. 대표적인 원인:

- GC(Garbage Collection) pause
- DB 락 경합 또는 슬로우 쿼리
- 커넥션 풀(Connection Pool) 고갈
- 특정 리소스에 대한 스레드 대기(Thread contention)

# 처리량 · 에러율 · 자원 사용률 지표

응답 시간과 함께 시스템의 실질적인 처리 능력과 안정성을 판단하려면 아래 지표들을 교차로 확인해야 한다.

## 1. TPS (Transactions Per Second)

- 초당 처리 가능한 트랜잭션(요청) 수 — 처리량(Throughput)의 핵심 지표
- 시스템이 실제로 감당할 수 있는 처리 용량을 나타냄
- **응답 시간이 짧아도 TPS가 낮다면** 병목(bottleneck)이 존재할 가능성이 있다 (예: 스레드 풀 크기 제한, 커넥션 풀 부족, 동시성 제어 로직에 의한 대기)
- 부하를 점진적으로 증가시키며 TPS 변화를 관찰하면, 시스템이 포화(saturation)되는 지점(더 이상 TPS가 증가하지 않고 오히려 응답 시간만 급증하는 구간)을 확인할 수 있다

## 2. 에러율 (Error Rate)

- 전체 요청 중 실패(5xx 응답, 타임아웃, 커넥션 거부 등)한 비율
- TPS가 높아 보여도 에러율이 함께 상승한다면, 이는 실질적인 처리 능력 향상이 아니라 **시스템이 한계를 넘어 요청을 처리하지 못하고 있다는 신호**
- 부하 증가 시 에러율이 급격히 증가하기 시작하는 지점 = 시스템의 실제 한계 용량(Capacity Limit)

## 3. CPU 사용률

- 서버 리소스 중 가장 기본적으로 확인해야 하는 지표
- CPU 사용률이 100%에 근접하면서 응답 시간이 급격히 증가한다면 → **CPU-bound 병목**
- 반대로 CPU 사용률은 낮은데 응답 시간이 느리다면 → I/O 대기(DB, 외부 API 호출, 디스크 I/O) 또는 락 경합 등 **다른 원인**을 의심해야 함
- CPU 사용률만으로는 원인 진단이 부족할 수 있으므로, 필요 시 다음 지표도 함께 확인하는 것을 권장:
    - 메모리 사용률 및 GC 빈도/소요 시간
    - 네트워크 I/O
    - DB 커넥션 풀 사용률 및 슬로우 쿼리

## 4. 종합 해석 — 지표를 함께 봐야 하는 이유

TPS · 에러율 · CPU 사용률은 독립적으로 보지 않고, 응답 시간 지표(1번 문서)와 반드시 교차 분석해야 한다.

**예시 시나리오**: TPS 상승 + 에러율 상승 + CPU 사용률 100% 근접 + 99th 백분위 응답 시간 급증 → 시스템이 한계 용량(Capacity Limit)에 도달했다는 명확한 신호

이처럼 하나의 지표만으로 결론을 내리지 말고, 부하 증가 구간별로 모든 지표를 함께 시계열로 비교하는 것이 성능 테스트 결과를 신뢰성 있게 해석하는 핵심이다.
