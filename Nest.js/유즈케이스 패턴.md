## 개요

NestJS에서 UseCase 기반 아키텍처는 Clean Architecture 원칙을 적용하여 비즈니스 로직을 중심으로 한 설계 방법입니다. 각 UseCase는 독립적인 비즈니스 시나리오를 담당하며, 테스트 가능성과 유지보수성을 높입니다.

---

## 아키텍처 개념

### UseCase 구조의 핵심

- **단일 책임**: 하나의 구체적인 비즈니스 기능을 수행
- **의존성 역전**: 인터페이스에 의존하며, 구체적인 구현에 의존하지 않음
- **테스트 가능성**: 순수한 비즈니스 로직으로 단위 테스트가 용이

### 기본 원칙

- 같은 도메인의 UseCase는 같은 모듈에 배치
- 모듈 간 통신은 인터페이스를 통해 수행
- 비즈니스 로직과 기술적 세부사항 분리

## UseCase 패턴 vs Application Service 패턴

### UseCase 패턴 (Clean Architecture)

```
Controller → UseCase → Repository/Service Interface
```

**특징:**

- 각 비즈니스 시나리오별로 독립적인 UseCase 클래스
- 복잡한 비즈니스 로직에 적합
- 높은 테스트 가능성

**예시:**

```typescript
@Injectable()
export class CreateUserUseCase {
  async execute(input: CreateUserInput): Promise<User> {
    // 특정 비즈니스 시나리오 구현
  }
}
```

### Application Service 패턴 (전통적 방식)

```
Controller → Service Interface → Service → Repository
```

**특징:**

- 관련 기능들을 하나의 서비스에 그룹핑
- 단순한 CRUD 중심 애플리케이션에 적합
- 구조가 단순하고 이해하기 쉬움

**예시:**

```typescript
@Injectable()
export class UserService implements UserServiceInterface {
  async createUser(data: CreateUserDto): Promise<User> { ... }
  async getUser(id: string): Promise<User> { ... }
  async updateUser(id: string, data: UpdateUserDto): Promise<User> { ... }
}
```

## 각 계층의 역할

### 1. Presentation Layer (프레젠테이션 계층)

**역할**: HTTP 요청/응답 처리, DTO 변환

```typescript
@Controller('users')
export class UserController {
  constructor(
    private readonly createUserUseCase: CreateUserUseCase,
    private readonly getUserUseCase: GetUserUseCase,
  ) {}

  @Post()
  async createUser(@Body() dto: CreateUserDto): Promise<UserResponseDto> {
    const result = await this.createUserUseCase.execute(dto);
    return this.toResponseDto(result);
  }
}
```

### 2. Application Layer (애플리케이션 계층)

**역할**: 비즈니스 시나리오 오케스트레이션, UseCase 구현

```typescript
@Injectable()
export class CreateUserUseCase {
  constructor(
    private readonly userRepository: UserRepository,
    private readonly userDomainService: UserDomainService,
    @Inject('NotificationServiceInterface')
    private readonly notificationService: NotificationServiceInterface,
  ) {}

  async execute(input: CreateUserInput): Promise<User> {
    // 1. 도메인 객체 생성
    const user = new User(input);
    
    // 2. 도메인 서비스를 통한 검증
    await this.userDomainService.validateUser(user);
    
    // 3. 저장
    const savedUser = await this.userRepository.save(user);
    
    // 4. 외부 서비스 호출
    await this.notificationService.sendWelcomeEmail(savedUser.email);
    
    return savedUser;
  }
}
```

### 3. Domain Layer (도메인 계층)

**역할**: 핵심 비즈니스 로직, 도메인 규칙

```typescript
export class User {
  private _id: string;
  private _email: string;
  private _status: UserStatus;

  constructor(props: UserProps) {
    this._id = props.id;

  }

  public changeEmail(newEmail: string): void {
    if (!this.isValidEmail(newEmail)) {

    }
    this._email = newEmail;
  }

  public canPlaceOrder(): boolean {
    return this._status === UserStatus.ACTIVE;
  }

  private isValidEmail(email: string): boolean {
    // 이메일 검증 로직
  }
}
```

### 4. Infrastructure Layer (인프라 계층)

**역할**: 외부 시스템 연동, 데이터 영속성

```typescript
@Injectable()
export class UserRepositoryImpl implements UserRepository {
  constructor(private readonly prisma: PrismaService) {}

  async save(user: User): Promise<User> {
    const userData = this.toPrismaData(user);
    const savedData = await this.prisma.user.upsert({
      where: { id: user.id },
      update: userData,
      create: userData,
    });
    return this.toDomainEntity(savedData);
  }

  private toDomainEntity(userData: any): User {
    return new User({
      id: userData.id,
      email: userData.email,
      status: userData.status,
    });
  }
}
```

## 의존성 관리

### 같은 모듈 내 의존성

```typescript
// 직접 주입
constructor(
  private readonly userRepository: UserRepository,
  private readonly userDomainService: UserDomainService,
) {}
```

### 다른 모듈 간 의존성

```typescript
// 인터페이스를 통한 주입
constructor(
  @Inject('UserServiceInterface')
  private readonly userService: UserServiceInterface,
  @Inject('NotificationServiceInterface')
  private readonly notificationService: NotificationServiceInterface,
) {}
```

### 모듈 설정

```typescript
@Module({
  imports: [
    TypeOrmModule.forFeature([UserEntity]),
    NotificationModule, // 다른 모듈 import
  ],
  providers: [
    // UseCase
    CreateUserUseCase,
    GetUserUseCase,
    
    // Repository
    {
      provide: 'UserRepository',
      useClass: UserRepositoryImpl,
    },
    
    // Service
    {
      provide: 'UserServiceInterface',
      useClass: UserService,
    },
  ],
  controllers: [UserController],
  exports: ['UserServiceInterface'], // 다른 모듈에서 사용할 수 있도록
})
export class UserModule {}
```

```

2. OrderController.createOrder()

3. CreateOrderUseCase.execute()
```

## Prisma와 Domain Entity

### Prisma Schema (데이터베이스 스키마)

```prisma
// prisma/schema.prisma
model User {
  id        String   @id @default(cuid())
  email     String   @unique
  name      String
  status    String   @default("ACTIVE")
  createdAt DateTime @default(now())
  updatedAt DateTime @updatedAt
  
  @@map("users")
}
```

### Domain Entity (비즈니스 로직)

```typescript
// src/modules/user/domain/entities/user.entity.ts
export class User {
  private readonly _id: string;
  private _email: string;
  private _status: UserStatus;

  constructor(props: UserProps) {
    this._id = props.id;
    this._email = props.email;
    this._status = props.status;
  }

  // 비즈니스 로직 메서드들
  public changeEmail(newEmail: string): void {

    }
    this._email = newEmail;
  }

```

### Repository에서 매핑

```typescript
@Injectable()
export class UserRepositoryImpl implements UserRepository {
  async findById(id: string): Promise<User | null> {
    const userData = await this.prisma.user.findUnique({ where: { id } });
    return userData ? this.toDomainEntity(userData) : null;
  }

  private toDomainEntity(userData: any): User {
    return new User({
      id: userData.id,
      email: userData.email,
      status: userData.status as UserStatus,
    });
  }
}
```

## 실무 적용 가이드

### 언제 UseCase 패턴을 사용할까?

**UseCase 패턴 적합한 경우:**

- 복잡한 비즈니스 로직이 많은 프로젝트
- 각 기능이 독립적으로 테스트되어야 하는 경우
- 도메인이 복잡하고 지속적으로 변경되는 경우

**Application Service 패턴 적합한 경우:**

- 단순한 CRUD 위주의 프로젝트
- 빠른 개발이 필요한 경우
- 팀이 작고 도메인이 단순한 경우

### 하이브리드 접근법

```typescript
// 단순한 CRUD는 Service로
interface UserServiceInterface {
  getUser(id: string): Promise<User>;
  updateUser(id: string, data: UpdateUserDto): Promise<User>;
}

// 복잡한 비즈니스 로직은 UseCase로
class UserRegistrationUseCase { ... }
class UserPasswordResetUseCase { ... }
```

### 주요 장점

1. **관심사 분리**: 각 계층이 명확한 책임을 가짐
2. **테스트 용이성**: 각 계층을 독립적으로 테스트 가능
3. **유지보수성**: 비즈니스 로직이 한 곳에 집중됨
4. **확장성**: 새로운 기능 추가 시 기존 코드에 미치는 영향 최소화
5. **모듈 독립성**: 각 모듈이 인터페이스를 통해 느슨하게 결합

### 구현 체크리스트

- [ ] 모듈별로 명확한 경계 정의
- [ ] Repository 인터페이스와 구현체 분리
- [ ] UseCase에서 비즈니스 로직 오케스트레이션
- [ ] 모듈 간 인터페이스를 통한 통신
- [ ] Domain Entity에 비즈니스 로직 캡슐화
- [ ] 의존성 주입을 통한 느슨한 결합
- [ ] 각 계층별 단위 테스트 작성
