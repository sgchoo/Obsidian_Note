## Nest.js 철학

Nest.js의 핵심 철학은 **"확장 가능하고 유지보수하기 쉬운 서버 사이드 애플리케이션을 구축하기 위한 구조적 접근"**입니다.

### 핵심 원칙

1. **모듈성과 관심사의 분리**: 독립적인 모듈로 애플리케이션을 구성
2. **의존성 주입**: 객체 간 결합도를 낮추고 테스트 가능한 코드 작성
3. **데코레이터 기반 선언적 프로그래밍**: 메타데이터를 통한 설정과 동작 정의
4. **계층화된 아키텍처**: Controller → Service → Repository 구조
5. **AOP (Aspect-Oriented Programming)**: 횡단 관심사 분리
6. **설정보다 관례**: 일관된 구조와 명명 규칙
7. **테스트 친화적 설계**: DI와 모듈화를 통한 쉬운 테스트

### 계층별 책임

```typescript
// Controller: HTTP 요청/응답 처리
@Controller('users')
@UseGuards(AuthGuard)
export class UserController {
  @Get(':id')
  @UseInterceptors(CacheInterceptor)
  async getUser(@Param('id') id: string) {
    return this.userService.findById(id);
  }
}

// Service: 비즈니스 로직
@Injectable()
export class UserService {
  constructor(private readonly userRepository: UserRepository) {}
  
  async findById(id: string) {
    return this.userRepository.findById(id);
  }
}

// Repository: 데이터 액세스
@Injectable()
export class UserRepository {
  async findById(id: string) {
    return this.userEntity.findOne({ where: { id } });
  }
}
```

## Nest.js 에러 로깅 전략

### 1. Exception Filters 활용 (기본)

전역 Exception Filter를 통해 모든 예외를 중앙에서 처리합니다.

```typescript
@Catch()
export class GlobalExceptionFilter implements ExceptionFilter {
  private readonly logger = new Logger(GlobalExceptionFilter.name);

  catch(exception: unknown, host: ArgumentsHost) {
    const ctx = host.switchToHttp();
    const response = ctx.getResponse();
    const request = ctx.getRequest();

    const status = exception instanceof HttpException 
      ? exception.getStatus() 
      : HttpStatus.INTERNAL_SERVER_ERROR;

    const errorResponse = {
      statusCode: status,
      timestamp: new Date().toISOString(),
      path: request.url,
      method: request.method,
      message: exception instanceof HttpException 
        ? exception.message 
        : 'Internal server error',
    };

    // 에러 로깅
    this.logger.error(
      `${request.method} ${request.url}`,
      exception instanceof Error ? exception.stack : exception,
    );

    response.status(status).json(errorResponse);
  }
}
```

### 2. 구조화된 로깅 시스템

Winston과 같은 로깅 라이브러리를 사용하여 구조화된 로그를 생성합니다.

```typescript
import * as winston from 'winston';

const logger = winston.createLogger({
  level: 'info',
  format: winston.format.combine(
    winston.format.timestamp(),
    winston.format.errors({ stack: true }),
    winston.format.json(),
  ),
  transports: [
    new winston.transports.File({ filename: 'error.log', level: 'error' }),
    new winston.transports.File({ filename: 'combined.log' }),
  ],
});
```

### 3. Interceptor를 통한 요청/응답 로깅

```typescript
@Injectable()
export class LoggingInterceptor implements NestInterceptor {
  private readonly logger = new Logger(LoggingInterceptor.name);

  intercept(context: ExecutionContext, next: CallHandler): Observable<any> {
    const request = context.switchToHttp().getRequest();
    const startTime = Date.now();

    return next.handle().pipe(
      tap(() => {
        const responseTime = Date.now() - startTime;
        this.logger.log(`${request.method} ${request.url} - ${responseTime}ms`);
      }),
      catchError((error) => {
        const responseTime = Date.now() - startTime;
        this.logger.error(
          `${request.method} ${request.url} - ${responseTime}ms - ERROR: ${error.message}`,
          error.stack,
        );
        throw error;
      }),
    );
  }
}
```

## try/catch 사용 원칙

### ❌ 권장하지 않는 방식 (Anti-pattern)

모든 곳에 try/catch를 사용하면 코드 중복과 복잡성이 증가합니다.

```typescript
// ❌ 모든 곳에 try/catch - 코드 중복과 복잡성 증가
@Controller('users')
export class UserController {
  async createUser(@Body() userData: CreateUserDto) {
    try {
      return await this.userService.createUser(userData);
    } catch (error) {
      this.logger.error('Controller error', error);
      throw error;
    }
  }
}

@Injectable()
export class UserService {
  async createUser(userData: CreateUserDto) {
    try {
      return await this.userRepository.save(userData);
    } catch (error) {
      this.logger.error('Service error', error);
      throw error;
    }
  }
}
```

### ✅ 권장하는 방식

Exception Filter가 모든 에러를 처리하므로 비즈니스 로직은 단순하게 유지합니다.

```typescript
// ✅ 깔끔한 비즈니스 로직
@Controller('users')
export class UserController {
  @Post()
  async createUser(@Body() userData: CreateUserDto) {
    // try/catch 없이 단순하게
    return await this.userService.createUser(userData);
  }
}

@Injectable()
export class UserService {
  async createUser(userData: CreateUserDto) {
    // 비즈니스 로직에 집중
    const user = await this.userRepository.save(userData);
    return user;
  }
}
```

### try/catch를 사용해야 하는 경우

#### 1. 에러 변환이 필요한 경우

```typescript
try {
  await this.externalApiCall();
} catch (error) {
  throw new BadRequestException('External service failed');
}
```

#### 2. 부분적 실패 처리

```typescript
async processUsers(userIds: string[]) {
  const results = [];
  for (const id of userIds) {
    try {
      const result = await this.processUser(id);
      results.push({ id, success: true, data: result });
    } catch (error) {
      results.push({ id, success: false, error: error.message });
    }
  }
  return results;
}
```

#### 3. 리소스 정리가 필요한 경우

```typescript
async uploadFile(file: Express.Multer.File) {
  let tempPath: string;
  try {
    tempPath = await this.createTempFile(file);
    return await this.processFile(tempPath);
  } finally {
    if (tempPath) {
      await this.cleanupTempFile(tempPath);
    }
  }
}
```

## Prisma 에러 처리

### 문제: Prisma 에러가 그대로 노출

```typescript
// ❌ PrismaClientKnownRequestError가 그대로 클라이언트에 전달됨
@Injectable()
export class UserService {
  async findUser(id: string) {
    return await this.prisma.user.findUniqueOrThrow({
      where: { id }
    });
  }
}
```

클라이언트 응답:

```json
{
  "error": "PrismaClientKnownRequestError",
  "code": "P2025",
  "message": "An operation failed because it depends on one or more records..."
}
```

### ✅ 해결: Prisma Exception Filter (권장)

모든 Prisma 에러를 중앙에서 일관되게 처리합니다.

```typescript
@Catch(PrismaClientKnownRequestError)
export class PrismaExceptionFilter implements ExceptionFilter {
  private readonly logger = new Logger(PrismaExceptionFilter.name);

  catch(exception: PrismaClientKnownRequestError, host: ArgumentsHost) {
    const ctx = host.switchToHttp();
    const response = ctx.getResponse();
    const request = ctx.getRequest();

    let status: HttpStatus;
    let message: string;

    switch (exception.code) {
      case 'P2025':
        status = HttpStatus.NOT_FOUND;
        message = 'Resource not found';
        break;
      case 'P2002':
        status = HttpStatus.CONFLICT;
        message = `Duplicate entry for ${this.getConstraintField(exception)}`;
        break;
      case 'P2003':
        status = HttpStatus.BAD_REQUEST;
        message = 'Invalid reference';
        break;
      default:
        status = HttpStatus.INTERNAL_SERVER_ERROR;
        message = 'Database operation failed';
    }

    const errorResponse = {
      statusCode: status,
      message,
      error: 'Database Error',
      timestamp: new Date().toISOString(),
      path: request.url,
    };

    this.logger.error(
      `Prisma Error ${exception.code}: ${exception.message}`,
      exception.stack,
    );

    response.status(status).json(errorResponse);
  }

  private getConstraintField(exception: PrismaClientKnownRequestError): string {
    const meta = exception.meta as any;
    return meta?.target?.[0] || 'field';
  }
}
```

### Prisma Exception Filter의 장점

1. **DRY 원칙**: 모든 Repository에서 동일한 에러 처리 반복 제거
2. **비즈니스 로직의 순수성**: Repository가 데이터 액세스에만 집중
3. **일관된 에러 응답**: 모든 Prisma 에러가 동일한 형태로 변환
4. **확장성**: 새로운 에러 코드 추가가 한 곳에서만 가능
5. **테스트 용이성**: 에러 처리 로직을 독립적으로 테스트 가능

## 권장 아키텍처

### 1. 전역 Exception Filter 등록

```typescript
// main.ts
async function bootstrap() {
  const app = await NestFactory.create(AppModule);
  
  app.useGlobalFilters(
    new GlobalExceptionFilter(),
    new PrismaExceptionFilter(),
  );
  
  await app.listen(3000);
}
```

### 2. 계층별 깔끔한 코드 구조

```typescript
// Repository: 순수한 데이터 액세스
@Injectable()
export class UserRepository {
  constructor(private prisma: PrismaService) {}

  async findById(id: string) {
    return this.prisma.user.findUniqueOrThrow({ where: { id } });
  }

  async create(data: CreateUserDto) {
    return this.prisma.user.create({ data });
  }
}

// Service: 비즈니스 로직에만 집중
@Injectable()
export class UserService {
  constructor(private userRepository: UserRepository) {}

  async getUser(id: string) {
    return this.userRepository.findById(id);
  }

  async createUser(userData: CreateUserDto) {
    return this.userRepository.create(userData);
  }
}

// Controller: HTTP 요청/응답 처리
@Controller('users')
export class UserController {
  constructor(private userService: UserService) {}

  @Get(':id')
  async getUser(@Param('id') id: string) {
    return this.userService.getUser(id);
  }

  @Post()
  async createUser(@Body() userData: CreateUserDto) {
    return this.userService.createUser(userData);
  }
}
```

### 3. 에러 처리 흐름

```
Request → Controller → Service → Repository → Prisma
                ↓
PrismaClientKnownRequestError (P2025)
                ↓
PrismaExceptionFilter
                ↓
HTTP 404 Response (Resource not found)
```

## 핵심 포인트

- **Exception Filter**가 모든 에러를 중앙에서 처리
- 비즈니스 로직에서는 try/catch 최소화
- 외부 라이브러리 에러는 전용 Exception Filter로 변환
- 각 계층이 고유한 책임에만 집중
- 일관된 에러 응답과 로깅 전략 유지

이러한 접근 방식을 통해 Nest.js의 철학에 부합하는 확장 가능하고 유지보수하기 쉬운 애플리케이션을 구축할 수 있습니다.
